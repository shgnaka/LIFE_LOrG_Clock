# Multi-device Sync Decisions v1

## Status

- Status: Baseline v1
- Date: 2026-06-13
- Scope: clock event synchronization before it becomes the primary path

## 1. Initial Topology

The initial supported topology is a full mesh among Full peers.

- Every pair of Full peers that must converge is paired directly.
- A peer sends only events authored by its own `deviceId`.
- A receiver accepts event batches only from the paired author device.
- Event forwarding, hub redistribution, and relay are not supported in v1.
- Viewer peers are not members of the write mesh.

This restriction remains until origin signatures, forwarding authorization,
loop prevention, and origin-scoped replication positions are implemented.

## 2. Cursor Semantics

- A cursor belongs to the source peer's event-store scan order.
- `sinceCursor` is exclusive.
- `nextCursor` is the source scan position committed by the response.
- The next request sends `sinceCursor = previous.nextCursor`; it does not add
  one.
- `nextCursor` may be present when `events` is empty. This is required when the
  source scanned rows that are not eligible for the requesting peer.
- `hasMore = true` requires a non-null, strictly advancing `nextCursor`.
- A receiver persists `lastSeenCursor` only after durable event handling and a
  successful ack exchange.
- A sender persists `lastSentCursor` only after the remote response confirms
  the complete submitted batch.
- Global pending progress is the minimum `lastSentCursor` across every active
  Full peer. A missing peer checkpoint keeps the data pending.

## 3. Delivery and Forwarding

An event's local database cursor is transport metadata, not event identity.
`eventId` is the duplicate key. A cursor assigned after receiving an event must
not be presented as the origin device's cursor.

Because v1 prohibits forwarding, a peer-specific checkpoint may scan past
events authored by other devices without sending them. The explicit
`nextCursor` preserves progress across those filtered rows.

## 4. Concurrent Clock Operations

The existing `clock.event.v1` schema is not sufficient for primary multi-writer
operation because stop and cancel do not identify the start session.

Before event sync becomes primary, `clock.event.v2` must add:

- `operationId`: stable across command/event coexistence and retries;
- `sessionId`: generated by `clock_started`;
- `targetSessionId`: required by `clock_stopped` and `clock_cancelled`;
- deterministic order key `(lamportCounter, deviceId, eventId)`.

Projection rules:

- replay order is the deterministic order key, never local database cursor;
- duplicate `operationId` is a no-op;
- stop/cancel affects only `targetSessionId`;
- concurrent starts create distinct sessions and are reported as a projection
  conflict until the product policy selects or closes one;
- invalid references remain recorded and produce a deterministic issue; they
  do not cause valid later events to disappear.

## 5. Durable Write Boundary

Local operations:

1. validate the requested domain operation;
2. durably append the event;
3. update event-derived read models;
4. project to the org file;
5. report success or recovery-required according to the result.

An event append failure is an operation failure. An org projection failure
after append is recovery-required and must not delete the event.

Remote operations require a durable application ledger:

1. durably store/deduplicate the event;
2. claim unapplied events;
3. apply the org/read-model projection;
4. durably mark the application result;
5. advance the peer cursor only after the batch is durably accounted for.

The current apply-before-append runtime is transitional and must be replaced
before primary cutover.

## 6. Command/Event Coexistence

- A peer capability record selects exactly one primary mutation path for clock
  operations: command or event.
- A single operation must not be published through both paths unless both
  representations carry the same `operationId`.
- Receivers deduplicate by `operationId` across paths.
- Mixed-version peers without `operationId` remain command-only.
- Rollback disables event transport but retains the local event log.

## 7. Identity

- `peerId` is the routing record identifier.
- `deviceId` is the stable event author identifier.
- signing public key and HTTPS transport credential are separate fields.
- a signing key change requires explicit re-pairing.
- revocation disables both signing trust and transport credentials.
- event sync remains direct-author-only until event envelopes are signed by
  the origin identity.

## 8. Primary-path Gate

Clock event sync cannot become primary until:

- `clock.event.v2` and cross-path `operationId` are implemented;
- the durable incoming application ledger is implemented;
- every Full peer uses the cursor rules in this document;
- full-mesh three-device convergence tests pass;
- partition/reconnect and arrival-order permutation tests pass;
- pairing v2 identity migration is complete.
